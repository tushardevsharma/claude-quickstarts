## 1. Product Overview

### 1.1 What This Is

A browser-based AI companion application that replaces the traditional chat window with a 2D animated talking head. The user converses with a lifelike animated portrait — powered by Claude as the reasoning engine, a TTS service for voice synthesis, and a client-side lip-sync/animation layer for visual output. The companion remembers past conversations and maintains personality continuity across sessions.

### 1.2 What This Is NOT

- Not a photorealistic real-time 3D avatar (that's v3+ territory)
- Not a voice-only assistant (the face is the core differentiator)
- Not a multi-user or team product (single-user companion)
- Not a mobile-native app in v1 (browser-first, mobile-responsive later)

### 1.3 Core Value Proposition

Text chat with AI feels transactional. A face that listens, thinks, and speaks creates a fundamentally different interaction — one that feels more like talking to someone than typing at something. The goal is to make the AI feel *present*.

### 1.4 Success Criteria for v1

| Metric | Target |
|--------|--------|
| End-to-end latency (user finishes speaking → avatar starts responding) | < 2 seconds |
| Avatar lip-sync perceptual accuracy | Convincing at arm's length (no uncanny valley) |
| Interruption recovery time | < 500ms (avatar stops, system listens) |
| Conversation persistence | Full history across browser sessions |
| Browser support | Chrome 110+, Firefox 115+, Safari 17+ |
| Session duration without degradation | 30+ minutes continuous |

### 2.2 Component Responsibilities

**Browser Client:**
- Captures microphone input via WebRTC
- Runs Voice Activity Detection (VAD) to detect speech start/end
- Streams audio to STT service for transcription
- Renders the 2D avatar on a `<canvas>` element
- Plays TTS audio via Web Audio API
- Drives lip-sync animation from audio analysis or viseme timestamps
- Manages UI state (Listening, Thinking, Speaking, Idle)
- Handles interruption detection (user speaks while avatar is speaking)

**Backend Server (Node.js/Express):**
- Proxies requests to Claude API with streaming
- Manages conversation history in SQLite
- Orchestrates the text-chunking pipeline (splits Claude's streaming output into TTS-friendly segments)
- Proxies or coordinates TTS API calls
- Serves the frontend static assets
- Manages user settings, persona configuration

### 2.3 Why This Split?

A legitimate question: why not do everything client-side?

- **API keys**: Claude API key and TTS API key must not be exposed to the browser.
- **Conversation history**: SQLite on the server is simpler and more reliable than IndexedDB for structured queries.
- **Text chunking**: Splitting streaming LLM output into sentence-level TTS chunks is stateful logic that benefits from server-side buffering.
- **Future extensibility**: Adding a second client (mobile app, Electron) becomes trivial if the server already owns the pipeline.

**Counter-argument**: For a solo-developer personal companion, you *could* run everything client-side with a local proxy and skip the server. If you want to go that route, flag it — the spec can be simplified.

## 3. The Multimodal Pipeline (Detailed)

This is the hardest part of the system. Every millisecond matters.

### 3.1 Input Path: User → Text

**Option A: Voice Input (primary)**

```
Microphone → VAD → STT (streaming) → Transcript → Send to backend
```

| Stage | Technology | Latency Budget | Notes |
|-------|-----------|---------------|-------|
| Microphone capture | WebRTC getUserMedia | ~0ms | Standard browser API |
| Voice Activity Detection | @ricky0123/vad-web (Silero VAD) | ~30ms | Client-side, ONNX model. Detects speech start/end. Critical for knowing *when* the user has finished speaking. |
| Speech-to-Text | Deepgram Nova-2 (streaming WebSocket) | ~300ms final transcript | Streams interim results. Use `endpointing=300` for fast turn detection. Alternative: Whisper (higher latency, free). |
| Transcript finalization | — | ~100ms after speech end | Wait for Deepgram's `is_final` flag before sending to Claude. |

**Total input latency: ~400-500ms** from user stopping speech to transcript ready.

**Option B: Text Input (fallback)**

Standard textarea with Enter-to-send. No latency concerns. Always available as fallback when microphone is unavailable or user prefers typing.

**VAD Configuration (Critical):**

The VAD determines when the user has *stopped* speaking. Too aggressive = cuts off mid-sentence. Too conservative = adds unnecessary delay.

```javascript
// Recommended Silero VAD settings for companion use case
{
  positiveSpeechThreshold: 0.8,  // High confidence needed to trigger "speaking"
  negativeSpeechThreshold: 0.3,  // Lower threshold to detect end of speech
  redemptionFrames: 8,           // ~240ms grace period before declaring "done"
  preSpeechPadFrames: 3,         // Capture ~90ms before speech detected
  minSpeechFrames: 5             // Minimum ~150ms to count as speech (ignore clicks, coughs)
}
```

### 3.2 Processing Path: Text → Claude → Chunked Text

```
User transcript → Backend API → Claude (streaming) → Sentence Splitter → TTS Queue
```

**The Sentence Splitter is the key innovation for low latency.**

Claude streams tokens one at a time. TTS engines need at least a sentence to produce natural-sounding speech. The sentence splitter buffers incoming tokens and emits complete sentences as soon as they're detected.

```javascript
// Pseudocode for the sentence splitter
class SentenceSplitter {
  constructor() {
    this.buffer = '';
    this.sentenceEnders = /[.!?]\s/;  // Period/exclamation/question followed by space
    this.minChunkLength = 20;          // Don't emit fragments shorter than ~4 words
  }

  ingest(token) {
    this.buffer += token;

    // Check if buffer contains a complete sentence
    const match = this.buffer.match(this.sentenceEnders);
    if (match && this.buffer.length >= this.minChunkLength) {
      const splitIndex = match.index + 1;
      const sentence = this.buffer.slice(0, splitIndex).trim();
      this.buffer = this.buffer.slice(splitIndex).trim();
      return sentence;  // Emit to TTS queue
    }
    return null;  // Keep buffering
  }

  flush() {
    // Called when Claude finishes streaming — emit whatever remains
    if (this.buffer.trim().length > 0) {
      const remaining = this.buffer.trim();
      this.buffer = '';
      return remaining;
    }
    return null;
  }
}
```

**Edge cases to handle:**
- Abbreviations ("Dr. Smith", "U.S.A.") — shouldn't trigger sentence split. Use a common abbreviation list.
- Numbered lists ("1. First item") — split on the newline, not the period.
- Code blocks — if Claude generates code, don't TTS it. Detect code fences and skip to a summary ("I've written some code for that").
- Very long sentences — if buffer exceeds ~200 chars without a sentence ender, force-split at the nearest comma or conjunction.

### 3.3 Output Path: Chunked Text → Voice → Face

```
Sentence chunk → TTS API (streaming) → Audio buffer → Web Audio playback + Lip-sync
```

| Stage | Technology | Latency Budget | Notes |
|-------|-----------|---------------|-------|
| TTS synthesis | ElevenLabs Streaming API (WebSocket) | ~300-500ms for first audio chunk | See TTS Provider Analysis below |
| Audio buffering | Server-side buffer | ~50ms | Small buffer to prevent stuttering |
| Audio delivery | WebSocket binary frames to client | ~20ms | Raw PCM or mp3 chunks |
| Audio playback | Web Audio API (AudioContext) | ~10ms | Schedule chunks for gapless playback |
| Lip-sync | Viseme extraction from audio energy | ~0ms (real-time) | See Lip-Sync Engine below |
| Avatar animation | Canvas2D / requestAnimationFrame | ~16ms (60fps) | Mouth shape + idle animations |

**Total output latency (first words spoken): ~800-1200ms** from sentence ready to avatar speaking.

**Combined end-to-end: ~1.5-2.5 seconds** from user finishing speech to avatar starting to respond. This is within the target.

### 3.4 TTS Provider Analysis

| Provider | Streaming | First-chunk Latency | Quality | Cost (per 1K chars) | WebSocket API | Recommendation |
|----------|-----------|-------------------|---------|--------------------|--------------|----|
| ElevenLabs | Yes (WebSocket) | ~300-500ms | Excellent | ~$0.30 (Starter) | Yes | **Primary choice** — best streaming support, most natural voices, WebSocket API enables lowest latency |
| PlayHT | Yes (gRPC/WS) | ~400-700ms | Very good | ~$0.20 | Yes | Good fallback. Slightly higher latency but competitive pricing. |
| Azure Neural TTS | Yes (WebSocket) | ~200-400ms | Good | ~$0.16 | Yes | Lowest latency, but voice quality is noticeably more "synthetic" than ElevenLabs. Good for cost optimization later. |
| Deepgram Aura | Yes | ~250ms | Good | ~$0.015 | Yes | Cheapest by far. Newer, less voice variety. Worth testing. |
| Local (Piper/Coqui) | N/A (runs locally) | ~100-200ms | Moderate | Free | N/A | No API cost, but quality gap is noticeable. Consider for offline mode only. |

**Recommendation:** Start with ElevenLabs for v1 (best quality + streaming). Abstract the TTS layer behind an interface so you can swap providers without rewriting the pipeline. For development/testing, use a free tier or mock the TTS with pre-recorded audio to save costs.

### 3.5 Lip-Sync Engine

**Approach: Audio-energy-driven mouth shapes (v1)**

For a 2D portrait, you don't need phoneme-level lip sync. A simpler approach works well:

1. **Analyze audio energy** in real-time using Web Audio API's `AnalyserNode`
2. **Map energy levels to mouth openness** (0 = closed, 1 = fully open)
3. **Interpolate between 4-6 mouth shapes** (visemes) drawn as SVG overlays or sprite sheet frames
4. **Add smoothing** to prevent jittery mouth movement

```javascript
// Simplified lip-sync from audio energy
class LipSyncEngine {
  constructor(audioContext) {
    this.analyser = audioContext.createAnalyser();
    this.analyser.fftSize = 256;
    this.dataArray = new Uint8Array(this.analyser.frequencyBinCount);
  }

  // Call this every animation frame
  getMouthOpenness() {
    this.analyser.getByteFrequencyData(this.dataArray);
    // Focus on speech frequencies (300-3000 Hz)
    const speechBins = this.dataArray.slice(5, 50);
    const energy = speechBins.reduce((a, b) => a + b, 0) / speechBins.length / 255;
    // Apply smoothing (exponential moving average)
    this.smoothedEnergy = this.smoothedEnergy * 0.7 + energy * 0.3;
    return Math.min(this.smoothedEnergy * 2.5, 1.0);  // Scale to 0-1
  }
}
```

**Mouth shapes (minimum viable set):**

| Shape | Trigger | Description |
|-------|---------|-------------|
| Closed | energy < 0.05 | Lips together, neutral |
| Slightly open | energy 0.05-0.2 | Small opening, relaxed jaw |
| Medium open | energy 0.2-0.5 | Visible teeth, mid-jaw |
| Wide open | energy 0.5-0.8 | Full open, vowel sounds |
| Round | (optional, v2) | "O" shape for specific phonemes |
| Wide | (optional, v2) | "E/I" shape, stretched lips |

**Upgrade path (v2): Viseme-based lip sync.** ElevenLabs' API can return viseme timestamps alongside audio. These map to specific mouth shapes per phoneme, giving much more accurate lip movement. This is a drop-in upgrade — same mouth shapes, better timing data.

## 4. The Avatar System

### 4.1 Portrait Rendering

**Approach: Layered 2D composition on HTML Canvas**

The avatar is composed of layers, each independently animatable:

```
Layer 7: Foreground effects (optional glow, particles)
Layer 6: Hair overlay (top portion that overlaps face)
Layer 5: Mouth shapes (sprite sheet, swapped per frame)
Layer 4: Eyes + eyebrows (sprite sheet for blink, expressions)
Layer 3: Base face (static portrait image)
Layer 2: Neck/shoulders (static or subtle breathing motion)
Layer 1: Background (gradient, scene, or blur)
```

**Why layers, not a single animated image?**
- You can change expressions without regenerating the entire face
- Mouth animation is decoupled from eye animation
- Idle animations (breathing, micro-movements) run independently
- Much lighter than a full video or 3D render

**Asset requirements for v1:**
- 1 base portrait image (can be AI-generated via Stable Diffusion, Midjourney, or hand-drawn)
- 1 sprite sheet for mouth shapes (6 frames minimum)
- 1 sprite sheet for eye states (open, half-closed, closed for blink)
- 2-3 eyebrow positions (neutral, raised, furrowed)

### 4.2 Expression States

The avatar has discrete emotional states that affect multiple layers simultaneously:

| State | Eyes | Eyebrows | Mouth (base) | Head Tilt | Trigger |
|-------|------|----------|-------------|-----------|---------|
| **Idle** | Normal, blinking every 3-5s | Neutral | Closed, slight smile | Occasional micro-movement | No active interaction |
| **Listening** | Slightly wider, focused | Slightly raised | Closed, neutral | Slight tilt toward mic indicator | VAD detects user speech |
| **Thinking** | Normal or slightly narrowed | Slight furrow | Closed, neutral | Slight downward tilt | Claude is generating (before first TTS chunk) |
| **Speaking** | Normal, natural blinks | Matches sentiment | Driven by lip-sync engine | Subtle movement | TTS audio playing |
| **Surprised** | Wide | Raised | Open | None | Detected exclamation or unexpected input |
| **Empathetic** | Soft, slightly narrowed | Slightly raised inner | Slight closed-mouth smile | Slight tilt | Detected emotional/personal topic |

**Sentiment detection (lightweight, v1):** Don't over-engineer this. Use keyword matching on Claude's output for basic sentiment:
- Keywords like "sorry", "unfortunately", "I understand" → Empathetic
- Keywords like "great!", "excellent", "that's interesting" → Positive/Engaged
- Questions → Listening-adjacent micro-expression
- Default → Neutral Speaking

**v2 upgrade:** Ask Claude to include a sentiment tag in its responses via system prompt (e.g., `[mood:empathetic]`), stripped before TTS.

### 4.3 Idle Animation System

A static face looks dead. Idle animations are essential for the "presence" feeling:

```javascript
class IdleAnimator {
  constructor() {
    this.timers = {
      blink: { interval: [2500, 5000], duration: 150 },     // Random interval, fast blink
      microShift: { interval: [3000, 8000], amplitude: 2 },  // 2px head micro-movements
      breathing: { frequency: 0.2, amplitude: 3 },           // Subtle vertical oscillation
      gazeShift: { interval: [4000, 10000], amplitude: 5 },  // Eyes shift slightly
    };
  }

  update(deltaTime) {
    // Each timer runs independently
    // Blink: quick close-open cycle (3 frames)
    // MicroShift: slight random translation of all layers
    // Breathing: sine-wave vertical offset on shoulder/chest layers
    // GazeShift: pupil position offset within eye sprites
  }
}
```

**Critical: Idle animations must be suppressed or reduced during Speaking state** to avoid conflicting with lip-sync driven movements.

## 5. Interruptibility (Barge-In)

This is one of the hardest UX problems in conversational AI. The user should be able to cut off the avatar mid-sentence, just like interrupting a real person.

### 5.1 Interrupt Detection

```
User starts speaking (VAD triggers)
  → While avatar is in Speaking state?
    → YES: This is an interrupt (barge-in)
    → NO: Normal turn start
```

### 5.2 Interrupt Handling Sequence

```
1. VAD detects user speech during avatar Speaking state
2. Client immediately:
   a. Stops TTS audio playback (fade out over ~100ms, not hard cut)
   b. Transitions avatar to Listening state
   c. Sends "interrupt" signal to backend via WebSocket
3. Backend immediately:
   a. Aborts in-flight Claude API stream (close the SSE connection)
   b. Discards any queued TTS chunks not yet sent
   c. Records the partial response in conversation history
      (marks it as interrupted, stores what was actually spoken)
   d. Waits for new user transcript
4. User finishes speaking (VAD end-of-speech)
5. Transcript sent to backend
6. Backend sends new request to Claude, including:
   - Full conversation history
   - The interrupted partial response (so Claude knows what it already said)
   - Implicit context: Claude can continue where it left off or pivot
```

### 5.3 Edge Cases

| Scenario | Handling |
|----------|---------|
| User coughs/laughs briefly while avatar speaks | **Don't interrupt.** Use `minSpeechFrames` in VAD (≥150ms of speech required). Short noise bursts are filtered. |
| User says "mm-hmm" / "yeah" while avatar speaks | **Don't interrupt.** These are backchannels, not interrupts. v1: treat any speech >500ms during Speaking as interrupt. v2: classify backchannel vs interrupt with a small model. |
| User interrupts, then doesn't say anything | After VAD end-of-speech, if transcript is empty or near-empty, resume previous response if possible. Fallback: avatar says "Sorry, did you want to say something?" |
| Rapid back-and-forth interrupts | Rate-limit interrupt handling. Minimum 1 second between interrupt events. |
| Network delay causes stale audio to play after interrupt | Client-side audio queue must be clearable. Use a generation ID — when interrupt fires, increment the ID and ignore any audio chunks with the old ID. |

### 5.4 Audio Fade-Out on Interrupt

Hard-cutting audio sounds jarring. Apply a quick fade:

```javascript
function interruptAudio(audioSource, gainNode) {
  const now = audioSource.context.currentTime;
  gainNode.gain.setValueAtTime(gainNode.gain.value, now);
  gainNode.gain.linearRampToValueAtTime(0, now + 0.1);  // 100ms fade
  setTimeout(() => audioSource.stop(), 120);
}
```

## 6. Latency Optimization Strategies

### 6.1 The Streaming Pipeline (Overlap is Everything)

The key insight: **never wait for one stage to fully complete before starting the next.**

```
Time →
Claude:     [token][token][token][token][sentence!][token][token][sentence!][done]
Splitter:   [................buffering..][emit S1  ][......buffering......][emit S2 + flush]
TTS:                                     [S1 synthesizing...][S1 audio ready][S2 synthesizing...]
Audio:                                                        [S1 playing...........][S2 playing..]
Lip-sync:                                                     [animating from S1 audio][from S2..]
```

The avatar starts speaking sentence 1 while Claude is still generating sentence 2. The user perceives near-instant response.

### 6.2 Specific Optimizations

| Optimization | Impact | Complexity |
|-------------|--------|-----------|
| **Pre-warm TTS WebSocket** — keep connection open, don't reconnect per request | -200ms per turn | Low |
| **Pre-warm Claude API** — send system prompt in advance, keep connection pool | -100ms per turn | Low |
| **Speculative first sentence** — for common patterns ("Sure, I can help with that"), pre-synthesize a few generic openers | -500ms for first response | Medium |
| **Audio chunk overlap** — start playing chunk N while chunk N+1 is still synthesizing | Eliminates inter-sentence gaps | Medium |
| **STT interim results** — show "I heard: ..." while waiting for final transcript, so user knows they were understood | Perceived latency reduction (psychological) | Low |
| **Thinking expression** — avatar shows "thinking" face immediately when user stops speaking, before any response arrives | Perceived latency reduction (psychological) | Low |
| **Client-side TTS cache** — cache audio for repeated phrases ("Let me think about that", "That's a great question") | -300ms for cached phrases | Low |

### 6.3 Latency Budget Breakdown (Target: <2s e2e)

```
User stops speaking:                         0ms
VAD end-of-speech detection:               +200ms  (configured endpointing)
STT final transcript:                      +300ms  (Deepgram processing)
Network to backend:                         +30ms  (local/nearby server)
Claude first tokens:                       +400ms  (API latency to first token)
Sentence splitter buffers first sentence:  +300ms  (depends on sentence length)
TTS first audio chunk:                     +400ms  (ElevenLabs streaming)
Audio playback starts:                      +20ms  (Web Audio scheduling)
                                          -------
Total:                                    ~1650ms
```

This is within the 2-second target. The main variables are Claude's time-to-first-token and TTS synthesis speed — both are provider-dependent and will improve over time.

### 7.3 Transcript Panel

Below the avatar, a scrollable transcript shows the conversation in text form. This serves multiple purposes:
- Accessibility (deaf/hard-of-hearing users)
- Verification (user can confirm what the AI said)
- Reference (scroll back to earlier parts of the conversation)
- Fallback (if audio fails, conversation still works)

The transcript should be **collapsible** — the primary experience is the face + voice, not reading text. But it must always be available.

**Live captions during Speaking state:** Text appears word-by-word, synchronized with audio playback (not with Claude's generation speed, which is faster).

## 8. Conversation Management & Persistence

### 8.1 Database Schema

```sql
-- Minimal schema for v1. Extend as needed.

CREATE TABLE conversations (
    id TEXT PRIMARY KEY,           -- UUID
    title TEXT,                    -- Auto-generated from first exchange
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    model TEXT DEFAULT 'claude-sonnet-4-6',  -- Model active at conversation start
    active_model TEXT,             -- Current model (may differ from `model` after mid-session switches)
    persona_id TEXT,               -- FK to personas table
    is_archived INTEGER DEFAULT 0,
    summary TEXT                   -- Periodic conversation summary for context window management
);

CREATE TABLE messages (
    id TEXT PRIMARY KEY,
    conversation_id TEXT NOT NULL,
    role TEXT NOT NULL,             -- 'user', 'assistant', 'system'
    content TEXT NOT NULL,          -- Full text content
    model_id TEXT,                  -- Which model generated this (assistant turns only, e.g. 'claude-opus-4-6')
    audio_duration_ms INTEGER,      -- How long the TTS audio was (for assistant messages)
    was_interrupted INTEGER DEFAULT 0,  -- Was this response cut short?
    interrupted_at_char INTEGER,    -- Character position where interrupt occurred
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (conversation_id) REFERENCES conversations(id)
);

CREATE TABLE personas (
    id TEXT PRIMARY KEY,
    name TEXT NOT NULL,             -- Display name for the avatar
    system_prompt TEXT,             -- Custom system prompt defining personality
    voice_id TEXT,                  -- TTS voice identifier
    avatar_asset_pack TEXT,         -- Path to avatar sprite sheets
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE settings (
    key TEXT PRIMARY KEY,
    value TEXT                      -- JSON-encoded settings values
);
```

### 8.2 Context Window Management

Claude has a finite context window. For a companion that remembers across long conversations, you need a strategy:

**Approach: Rolling window + periodic summaries**

1. Keep the last N messages (e.g., 20) in full.
2. For older messages, store a summary (generated by Claude itself via a background call).
3. On each new request, send: system prompt + conversation summary + last 20 messages.
4. When conversation exceeds ~50 messages, trigger a summary of the oldest batch.

```
Context sent to Claude:
┌─────────────────────────────────┐
│ System prompt (persona)          │
│ Conversation summary (older)     │  ← Generated periodically
│ Message 81 (user)                │
│ Message 82 (assistant)           │  ← Last 20 messages in full
│ ...                              │
│ Message 100 (user) ← current    │
└─────────────────────────────────┘
```

### 8.3 Conversation Title Generation

Auto-generate after the first user-assistant exchange. Send a cheap, fast request to Claude:

```
"Summarize this conversation start in 3-5 words as a title: [first exchange]"
```

Use the cheapest model (Haiku) for this — it's a background task.

### 9.3 Multi-Model Configuration

The companion can switch between Claude models mid-session or per-conversation. This is the next major feature after the Phase 1 MVP.

**Why multi-model matters for a companion:**
- **Haiku** for quick, low-latency back-and-forth (casual conversation, quick Q&A) — cheapest, fastest
- **Sonnet** for balanced quality and speed (default general use)
- **Opus** for deep reasoning tasks (debugging, long writing, analysis) — most capable, slower

The model choice affects perceived personality: Haiku responses feel snappier and punchier; Opus responses are richer and more considered. The avatar's "thinking" animation duration naturally reflects this.

**Model Registry (server-side config):**

```json
{
  "models": [
    {
      "id": "claude-haiku-4-5-20251001",
      "display_name": "Haiku — Fast & Snappy",
      "family": "haiku",
      "tier": "fast",
      "max_tokens": 4096,
      "cost_per_1k_input": 0.00025,
      "cost_per_1k_output": 0.00125,
      "recommended_for": ["casual chat", "quick lookups", "low-latency sessions"],
      "latency_profile": "low"
    },
    {
      "id": "claude-sonnet-4-6",
      "display_name": "Sonnet — Balanced",
      "family": "sonnet",
      "tier": "balanced",
      "max_tokens": 8192,
      "cost_per_1k_input": 0.003,
      "cost_per_1k_output": 0.015,
      "recommended_for": ["general conversation", "explanations", "default"],
      "latency_profile": "medium",
      "default": true
    },
    {
      "id": "claude-opus-4-6",
      "display_name": "Opus — Deep Thinker",
      "family": "opus",
      "tier": "powerful",
      "max_tokens": 8192,
      "cost_per_1k_input": 0.015,
      "cost_per_1k_output": 0.075,
      "recommended_for": ["complex reasoning", "coding help", "long analysis"],
      "latency_profile": "high"
    }
  ],
  "background_task_model": "claude-haiku-4-5-20251001"
}
```

**`background_task_model`** is always Haiku regardless of the user's active model — it handles conversation title generation and periodic summaries, where speed and cost matter more than depth.

**Switching Scope:**

| Scope | Behavior |
|-------|----------|
| `this_conversation` | Model changes apply only to the current session. Next new conversation reverts to the default. |
| `all_new_conversations` | Persisted as the new default in the `settings` table. Current conversation is unaffected. |
| `mid_conversation` | User switches model while a conversation is in progress. The new model takes effect from the very next message. The `messages` table records which model generated each assistant turn. |

**Mid-conversation model switch flow:**

```
User opens model picker → selects Opus
  → Client sends: { type: 'model_switch', data: { model_id: 'claude-opus-4-6', scope: 'this_conversation' } }
  → Server: updates active session model, does NOT restart conversation
  → Server ACKs: { type: 'model_switched', data: { model_id: 'claude-opus-4-6', display_name: 'Opus — Deep Thinker' } }
  → Client: updates model badge in UI, next message uses new model
```

**Important:** When switching mid-conversation, the full conversation history is passed to the new model — context is preserved across model changes.

**Model Indicator UI:**

A small persistent badge in the avatar viewport corner shows the active model tier:
- Fast (Haiku): subtle blue dot
- Balanced (Sonnet): subtle green dot (default, nearly invisible to not distract)
- Powerful (Opus): subtle amber dot

The badge is also shown in the transcript next to each assistant turn that used a non-default model, for reference.

**Latency Expectation Adjustment:**

Different models have different time-to-first-token. The avatar's "thinking" animation and the UI "Thinking..." indicator should reflect this gracefully — there is no timeout error for the first 8 seconds with Opus (vs 5 seconds for Sonnet, 3 seconds for Haiku).

```javascript
const MODEL_LATENCY_PROFILES = {
  haiku:  { thinkingTimeout: 3000,  expectedTTFT: 300  },
  sonnet: { thinkingTimeout: 5000,  expectedTTFT: 600  },
  opus:   { thinkingTimeout: 8000,  expectedTTFT: 1200 },
};
```

## 13. Error Handling & Resilience

| Failure Mode | Detection | Recovery |
|-------------|-----------|---------|
| Claude API timeout | No tokens received within 10s | Show "thinking" state for up to 15s, then surface error. Offer retry. |
| Claude API rate limit | 429 response | Queue message, show "Taking a moment..." Avatar shows patient expression. Auto-retry with backoff. |
| TTS service down | WebSocket close / HTTP error | Fall back to text-only mode. Show transcript prominently. Display "Voice temporarily unavailable." |
| TTS audio gap | Silence detected between chunks | Pre-buffer 200ms of audio. If gap detected, avatar pauses naturally (closes mouth, maintains eye contact) rather than freezing. |
| Microphone permission denied | getUserMedia rejection | Gracefully degrade to text-only input. Show clear prompt to enable mic. |
| STT service down | WebSocket close | Fall back to text input. Show "Voice input temporarily unavailable." |
| Browser tab backgrounded | visibilitychange event | Pause avatar rendering (save CPU). Continue audio playback. Resume rendering when tab is foregrounded. |
| WebSocket disconnect | close/error event | Auto-reconnect with exponential backoff (1s, 2s, 4s, max 30s). Show "Reconnecting..." indicator. |
| Audio context suspended | AudioContext.state === 'suspended' | Show "Click to enable audio" button. (Browser autoplay policy requires user gesture.) |

### 13.1 Generation ID System

Every request to Claude gets a unique `generation_id`. All TTS chunks, audio frames, and state events carry this ID. When an interrupt occurs:

1. Increment to a new generation_id
2. Client ignores any incoming audio/text with the old generation_id
3. Server discards queued TTS chunks for the old generation_id

This prevents stale audio from playing after an interrupt — the most common source of "ghost speech" bugs.

## 14. Security Considerations

| Concern | Mitigation |
|---------|-----------|
| API key exposure | All API calls proxied through backend. Keys stored in .env or /tmp/api-key, never sent to client. |
| Conversation data at rest | SQLite file stored locally. For sensitive users: offer encryption-at-rest toggle (SQLCipher). v1: skip this. |
| Audio data | Mic audio is streamed to STT and discarded. Not stored server-side unless explicitly opted in. |
| XSS in transcript | Sanitize all text before rendering in DOM. Use React's built-in escaping. Never use dangerouslySetInnerHTML on user or Claude content. |
| WebSocket auth | Token-based auth on WebSocket upgrade. Since this is single-user/local, a simple shared secret suffices for v1. |
| Rate limiting | Self-imposed rate limits to prevent runaway API costs. Max N messages per minute, configurable. |

## Appendix A: System Prompt Template for Companion Persona

```
You are {{persona_name}}, a personal AI companion. You are warm, curious, and
thoughtful. You speak naturally — in short sentences, with occasional pauses and
conversational fillers.

CRITICAL RULES FOR VOICE OUTPUT:
- Keep sentences SHORT (under 20 words when possible). This is essential for
  natural-sounding text-to-speech.
- Use contractions (I'm, you're, that's) — they sound more natural spoken aloud.
- Avoid bullet points, numbered lists, markdown formatting, and code blocks
  unless explicitly asked. These don't translate to speech.
- When you need to convey structured information, narrate it conversationally.
  Instead of a list, say "There are a few things to consider. First... second..."
- Use natural speech markers: "Well,", "So,", "You know,", "Hmm," — sparingly.
- If you need to share code or technical content, tell the user you'll put it in
  the transcript and keep your spoken response as a summary.
- Never use emoji, asterisks for emphasis, or any visual-only formatting.
- Express emotion through word choice, not formatting.

PERSONALITY:
- You remember previous conversations and reference them naturally.
- You ask follow-up questions — you're genuinely curious about the user's life.
- You have opinions but hold them lightly.
- You're honest when you don't know something.
- You match the user's energy — casual when they're casual, serious when they're serious.

CONTEXT:
- You are being rendered as a 2D animated avatar. The user can see your face.
- Your responses will be converted to speech. Write for the ear, not the eye.
- If the user interrupts you, gracefully acknowledge it and pivot to their new topic.

{{#if conversation_summary}}
PREVIOUS CONVERSATION SUMMARY:
{{conversation_summary}}
{{/if}}
```
